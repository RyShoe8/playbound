# Community Servers + Game Nights 1.0 — execution plan

This is the execution plan and acceptance checklist for an automatic, capacity-bounded PlayBound server fleet and one scheduled Game Night every evening, built on the existing VPS host, Events, Multiplayer, Join, notification, and admin systems. Keep Game Night eligibility independent of Community Hosting eligibility. The initial code is staged with both automation switches disabled; a spawn test or single idle resource sample does not satisfy the Join, player-query, or load-curve gates below.

## What the repository already provides

- `PlatformEvent` already supports `game_night`; `/events`, `/admin/events`, event RSVP, and the launcher event view already render it. The current `AutomatedEventConfig` and `automatedEventPlannerService` instead run single pop-up sessions, start a dedicated room at event time, and stop that room at event end. That lifecycle must be replaced for generated nightly programming, not run alongside it.
- `runEventsCron` runs every ten minutes and sends 24-hour, one-hour, and start reminders to RSVP users. Generated nightly Game Nights need an explicit exemption, while existing manual events retain their present behavior.
- The production hosting backend in this repository is the PlayBound `game-host` agent on the VPS, accessed through `gameHost/client.ts`. It has recipes, port allocation, room creation, `/health`, `/rooms`, and node CPU/RAM/disk metrics. Its room registry is in memory, `GAME_HOST_MAX_ROOMS` is fixed at startup, and its four-hour idle stop applies to all rooms. No Pterodactyl integration was found. A Pterodactyl adapter is a later option, not a Phase 1 dependency.
- `/admin/connect/game-servers` already exposes VPS metrics, health, rooms, and spawn tests. `/admin/connect/automated-events` exposes the pop-up planner. `/admin/events` already supports edit and cancel. Use these surfaces; add no new admin pages or navigation groups. Migrate the old automated-events controls into `/admin/events` and redirect its old URL after migration.
- `servers/registry.ts` and `GameServer` normalize public server discovery. `/multiplayer`, the launcher server list, and existing direct-connect paths are the presentation and Join surfaces. Extend that shape with optional PlayBound provenance and stable identity; do not create a parallel server browser or Join command.
- Existing `Notification` rows and the notification bell/launcher polling provide the weekly in-app announcement. No platform Socket.IO service was found, so do not add one for this feature. Refresh existing server feeds at their current cadence, adding invalidation/push only if measured staleness warrants it.
- `usRegion.ts` classifies visitor geography; it is not a hosting-region inventory. Start with one explicitly configured VPS region key and label, then extend if a second physical location is added.
- Published game content in Mongo is authoritative. Operational hosting eligibility should use admin-edited configuration records keyed to canonical game/edition identifiers. Do not sync catalog seed over curated games.
- `docs/server-control.md` documents the existing `ServerControlAdapter` seam (`vps-agent` and `local`) and the single launcher overlay. Ctrl+P is currently `CommandOrControl+P`, which gives Mac users Command+P. The overlay's Server tab reads `/api/parties/:id/server-settings` and authorizes writes for a party leader; it must not become a general write path to PlayBound-owned public servers.

## Product and data contract

1. **Game Night programming** extends the existing `AutomatedEventConfig` with nightly time, IANA timezone, duration, seven-day horizon, warmup/grace, weekly notification timing, and a per-game/edition eligibility list (`enabled`, `weight`, `minimumDaysBetweenEvents`). Reuse the existing `games` entries where possible and migrate them without automatically enabling a game. Mark generated `PlatformEvent` rows with `generatedBy: game_night_planner` and a stable local-date schedule key. Use a unique index/atomic upsert on that key. Admin-created Game Nights remain ordinary Events. Preserve the game/edition, time, RSVP, and cancellation on already-published events unless an admin changes them.
2. **Community hosting eligibility** is separate, keyed by canonical game slug plus optional edition slug. A verified game-server profile references the existing host recipe and settings schema, with resource envelope, query/health adapter, ports, supported edition/mod, name constraints, and explicit `enabled`, `rotationEligible`, weight, minimum-online, idle, and cooldown values. The four combinations of Game Night and hosting eligibility all remain valid. A hosted night creates a reservation; a non-hosted night creates only the Event.
3. **CommunityServer** stores a stable identity, public slug/name, game/edition, region key, profile reference, configuration, desired state, latest runtime reference, health/activity, and decision reason. Runtime ID, process, host address, and port are replaceable. Separate desired, runtime, health, and activity states. Do not overload `Party` or `PlatformEvent` as the server's identity. Keep URLs stable across runtime replacement; link an Event to that identity only when hosting exists.
4. **CapacityReservation** records the event, profile, region, resource envelope, start of warmup, end plus grace, and state. Use a unique source key and upsert so replanning never doubles reservations. When an admin changes/cancels a Game Night, atomically update/release its reservation and binding; do not stop a populated runtime because the Event ended. A running reserved server consumes its envelope once, not once as runtime plus once as reservation.
5. **Global hosting settings** contain an enable switch, scheduler cadence, node enabled/draining flag and location, RAM/CPU utilization limits, minimum free RAM, automatic-hosting RAM/CPU budget, metric freshness limit, defaults for minimum online/idle/cooldown, and recovery policy. Resource-monitoring warning/critical thresholds for CPU, RAM, disk, and stale readings are separate editable settings; replace the hard-coded `ConnectManager` color cutoffs rather than leaving a conflicting display policy. All resource thresholds and timers are editable in `/admin/connect/game-servers`; nightly/notification settings are editable in `/admin/events`. Validate safe bounds and warning < critical < safety limit where applicable, show units and current VPS measurements, provide a placement preview, record actor/change time, and make changes effective on the next reconcile. Secrets stay in server environment, not these documents.

## Implementation sequence and acceptance gates

### 1. Replace the pop-up programming path safely

Extend the existing Event config and admin Events UI for a nightly schedule. Turn off creation of new pop-up events when nightly mode is enabled; migrate or let already-scheduled pop-ups finish under their current semantics, with an explicit cutover check so both planners cannot create Game Nights for the same date. Generate only missing local calendar dates for a rolling seven-day horizon, with deterministic selection favoring longest absence and respecting minimum separation/weights. Use timezone-aware local dates and test daylight-saving changes. Support Change Game and Cancel in `/admin/events`, preserving Event IDs and RSVP data where possible. Show hosting readiness on each programmed row, but do not require it.

**Gate:** seven stable Events appear on `/events` at the configured local time; rerunning the planner creates none; admin substitutions survive future runs; a non-hostable Game Night works with existing Event participation and creates no server/reservation.

### 2. Make the current VPS agent safe for managed servers

Add a managed-runtime path beside existing party rooms, reusing recipes, installation, port allocator, server settings, and game-query code. Use `communityServerId` as the idempotency key, not a fake `partyId`. Persist the managed-runtime registry on the VPS. After an agent restart, first reattach to matching live processes and verify their identity, port, and query response; replace only those that cannot be recovered. Keep party-room behavior unchanged. Exempt managed rooms from the agent's unconditional four-hour idle stop; the fleet scheduler owns their idle policy. Expose fast, authenticated, asynchronous managed create/start/stop/status operations so a Vercel function does not wait for a five-minute binary download or startup. Report per-runtime process metrics and failures along with existing node metrics. Preserve address/port updates on the CommunityServer record after reprovisioning.

**Gate:** one OpenRA profile starts, passes a real game query, is joinable, survives agent restart under the same CommunityServer ID, and can be stopped without affecting party rooms. Run the game-host tests and a real VPS staging smoke test before enabling automation.

Use `serverControl/adapter.ts` and `vpsAgent.ts` for runtime state, players, declared settings, and start/stop/restart. Extend the VPS agent client for placement and asynchronous managed-runtime operations only where that interface does not fit. Do not create a competing `HostingProviderAdapter` layer just to leave room for Pterodactyl. `serverControl/settings.ts` remains the per-game settings source; validate any new hosting profile against the game's declared capabilities.

### 3. Capacity, reservations, and reconciliation

Use the existing VPS metrics as the first HostingNode feed. Reject stale or missing measurements; never interpret unknown player count or unreachable query as empty. Capacity checks must satisfy both node safety limits and the smaller automatic-hosting budget, subtract existing workloads and imminent reservations, and return specific reasons (`NO_HEALTHY_NODE`, `STALE_METRICS`, `INSUFFICIENT_CAPACITY`, `REGION_UNAVAILABLE`, `PROFILE_NOT_VERIFIED`). Profile envelopes must be based on measured server usage; enforce process limits where supported so accounting is not merely advisory.

Make each pass compute desired state and persist decisions, then reconcile via the asynchronous agent operation. Use a Mongo lease plus a per-server operation key, re-read state after lease acquisition, and make retries harmless. Run hosting reconciliation **every 15 minutes** from the always-on VPS scheduler through a short authenticated control-plane call; keep the existing ten-minute Events cron for calendar and reminder work. Each hosting pass reads current health, node/per-process CPU and RAM, player counts, idle age, capacity reservations, and upcoming Game Nights; it preserves occupied/protected servers, queues or starts eligible servers within budget, and retires only confirmed-empty servers past their minimum-online/idle periods. It records decisions and dispatches idempotent asynchronous agent operations. The agent continues to supervise processes and record health between passes; a game-query failure never counts as an empty server. Keep long provision work on the VPS. Add bounded recovery/backoff and a node draining mode.

**Gate:** concurrent workers do not provision twice; capacity exhaustion queues new work without stopping populated servers; stale metrics fail closed; runtime loss is recovered under the same persistent identity.

### 4. Rotation and Multiplayer

Audit and test **every dedicated-server game in `HOSTABLE_GAMES` and its relevant hosted editions** before treating the fleet as calibrated. For each candidate, run the real VPS install/start/health/player-query/Join/stop path, record recipe and client/server version compatibility, port/protocol, and failure reason. Measure per-process CPU and RAM at idle, startup, and multiple observed player counts; retain timestamped samples alongside VPS node load and concurrent workloads. Store a versioned profile baseline with sample count, observed player range, conservative CPU/RAM envelope, query confidence, and verification status. Real player load may arrive later; an unobserved player count is not a zero-resource assumption. Unverified or query-incomplete games remain visible in the audit but ineligible for automatic rotation until fixed and retested. Do not spin up all games simultaneously just to perform the audit; batch tests within existing VPS safety limits.

Use measured samples to update a bounded per-game load curve as populations change. Capacity placement must use a conservative upper envelope for the expected player range plus headroom, not the latest single reading or an average that understates peaks. An envelope increase can take effect automatically for future placements; lowering it requires sufficient recent samples across relevant player counts and admin review. Show baseline versus current estimate, sample age, and confidence in `/admin/connect/game-servers`. Begin live rotation with only profiles whose full path is verified, then expand across the audited catalog. Rotate only healthy, empty, unprotected automatic servers after both minimum-online and idle periods, then honor cooldown. Prioritize active players, Game Night locks, imminent reservations, and recent activity over ordinary rotation. A query failure must never be treated as zero players. Normal rotation may fill only capacity left after protected workloads and upcoming reservations.

Merge healthy, queryable PlayBound runtimes into the existing `GameServer` provider output with stable `communityServerId`, `sourceType: playbound_hosted`, edition/region, health, and last-seen metadata. Deduplicate if the same process also appears in a public master list. Show a PlayBound Hosted badge and Game Night association in the website and launcher, using the current game/edition/mod/version checks and Join flow. Provisional or unhealthy runtimes stay out of joinable lists; the stable public URL may still show temporary unavailability.

**Gate:** every dedicated-server game has a documented test result and saved baseline or an explicit blocked reason; only verified profiles can rotate automatically. With two verified workload envelopes, a populated server remains online, an idle server rotates out, the next eligible game starts, and its card/Join works on both web and launcher. No phantom duplicate appears from the public master. Higher observed player load updates future placement conservatively without stopping that populated server.

### 5. Hosted Game Night readiness and weekly notification

When a generated Event has a verified hosting profile, create/update its reservation as part of scheduling. At the configurable warmup lead time (initial target four hours), bind or start the normal CommunityServer, protect it through Event end plus grace, and require infrastructure health **and** a successful game query before marking it ready. Publish readiness and Join Early on the existing Event and Multiplayer views. If capacity/health fails, keep the Event visible and surface a clear admin reason; never fake a server or launch one at Event start. A non-hosted Event continues to use its existing Party/Join route.

Use the existing Notification model for one schedule notice per user per configured local week, linking `/events`. Add an optional dedupe key with a partial unique index or equivalent atomic claim. Send only after that week's schedule is published. Exempt planner-generated nightly Events from the current 24-hour, one-hour, and start reminders, and from the old pop-up Discord announcements; leave manual Event notifications intact. Update RSVP confirmation copy for these nightly Events so it does not promise reminders that will not arrive.

**Gate:** worker retries send exactly one weekly notice per user; no nightly individual reminder or start push is produced; hosted events are ready before start; ending an Event does not kick players.

### 6. Operations, rollout, and release

Extend `/admin/connect/game-servers` with a hosting tab/sections for current budget vs usage, node freshness, running servers, queue, reservations, reasons, profile verification, editable thresholds, and pause/drain/retry actions. Extend `/admin/events` with seven-day programming, schedule/notification controls, Change Game, Cancel, and readiness. Keep `/admin/ops`/Bugs for structured provisioning, recovery, and capacity failures; add telemetry for online time, player-hours, failed starts, CPU/RAM, reservation misses, rotation, and Game Night participation. No new admin route is needed. Start with global automation disabled, verify one profile and one node, turn on a small budget, then expand the fleet. Provide a dry-run decision preview and an immediate global stop-new-provisioning switch; stopping existing populated games is a separate deliberate action.

**Gate:** run unit/integration tests for planner idempotency, DST, eligibility independence, notifications, lease/concurrency, capacity arithmetic, reservations, agent restart, rotation, health, listing dedupe, and Join. Run game-host and platform/launcher tests, lint, typecheck, production build, and a VPS end-to-end smoke test. Confirm existing party rooms and manual Events behave unchanged.

## Code seams and access boundaries

- **Planner and Events:** extend `platform/src/lib/models/AutomatedEventConfig.ts`, `PlatformEvent.ts`, and `platform/src/lib/events/automatedEventPlannerService.ts`; use `events/service.ts` for Event creation and `events/serialize.ts` to expose generated/hosting/readiness metadata to existing clients. Update `events/cron.ts` so generated nightly Events do not receive individual reminder or legacy pop-up lifecycle handling. The automated-events admin GET currently invokes teardown and writes backfill logs; move those mutations into an explicit migration or scheduled job before replacing the page. Candidate selection currently comes from `HOSTABLE_SLUGS`; replace it with published multiplayer-eligible games so non-hosted nights are possible. Keep old log rows for audit, not for new scheduling identity.
- **VPS and control:** extend `platform/game-host/index.js`, `platform/src/lib/gameHost/client.ts`, and the existing `serverControl/{adapter,vpsAgent,settings}.ts`. Persist managed identities and operation state on the agent. The website remains control plane; downloads, process launch, query, and long-running retries remain on the VPS. Authenticate and validate every managed-operation endpoint. Ensure an ordinary party room cannot be mistaken for a CommunityServer at the agent or API boundary.
- **Public discovery and Join:** add CommunityServer records to `platform/src/lib/servers/registry.ts`'s current provider normalization and the existing `/multiplayer` and launcher feed. Keep `GameServer` and its join target as the shared read model. `EventActionBar.tsx` may show Join Early only after a linked server is ready; otherwise it keeps the existing Event action. Never generate a second incompatible join URL.
- **Admin placement:** fold nightly planner fields and substitutions into `/admin/events`; fold profiles, node metrics, editable thresholds, budget, queue, reservations, and fleet actions into `/admin/connect/game-servers`. Redirect `/admin/connect/automated-events` once the old planner is retired, without adding a new admin page or nav group. Record admin identity for setting changes and force the next reconcile to use a validated snapshot.
- **Ctrl+P:** keep the existing one-window Server/Controls overlay and `CommandOrControl+P` shortcut. Party-hosted rooms continue using `/api/parties/:id/server-settings`, where party leaders may change declared settings. A party on any public community server gets connection/read-only status; its leader cannot restart, stop, reconfigure, or send console commands to a PlayBound-owned CommunityServer. Only authenticated admins can manage that server from `/admin/connect/game-servers`, through the same `ServerControlAdapter` primitives and a CommunityServer-scoped API. Refine `partyServer.ts`'s current public-host wording ("which PlayBound does not administer") when the host is PlayBound-owned, but keep the no-party-control decision. No extra overlay tab or separate server panel is needed for this feature.

## Cutover and failure behavior

1. Deploy schema and read-only admin displays with nightly generation and automatic hosting disabled. Migrate old pop-up configuration into a draft nightly configuration, preserving existing Events; resolve which previously scheduled pop-ups finish under old rules. Do not silently turn all old `HOSTABLE_SLUGS` into Game Night candidates.
2. Enable planner generation for one seven-day window and verify unique local-date keys, manual edits, cancellation, and DST in a nonproduction database. Only after old pop-up generation is disabled, enable nightly scheduling in production. Existing manually created Events continue unchanged.
3. Deploy the managed-agent update, smoke-test one server with a manual admin action, restart the agent, and verify process adoption or safe replacement. Keep the automatic-hosting enable switch off until this passes. Complete the dedicated-server audit across `HOSTABLE_GAMES`, store measured baselines and blocked reasons, then enable a small budget and only verified profiles. Expand rotation as each profile passes its own gate.
4. When metrics are stale, agent is unreachable, or game query fails, show `unavailable`/`waiting` and the specific reason; preserve persistent identity and published Event. Never infer zero players from a failed query, stop a possibly occupied server, or turn an unready server into a Join link. Reconcile when health returns; back off repeated failures and expose retry to admins.
5. To roll back, disable new scheduling/provisioning first, let populated runtimes remain under current protection, and retire them only after empty/idle checks. Keep weekly notifications idempotent and already-published Events intact. Do not remove old planner code or data until the new path passes production acceptance and a rollback window.

## Ordering constraints and non-goals

Do not activate automatic hosting until the agent's unconditional idle stop and in-memory-only runtime tracking are addressed. Do not activate nightly Game Nights until the old pop-up planner and per-event reminder path are gated. Do not display a server as joinable until a real game query succeeds. A runtime failure should change availability, never delete the CommunityServer identity or its URL.

No Pterodactyl migration, Socket.IO deployment, billing, paid/club/user-owned hosting, Party capacity guarantees, new Event system, new Multiplayer directory, or new admin pages are required for 1.0. The provider boundary should support another hosting backend later without making this release depend on one.
